# PROJECT_RULES.md — 通用工程开发规则（项目无关模板）

> **用途**：一套适用于任意工程项目的通用开发规则基线，提炼自 vibe-coding 工作流
> （`.agents/skills/vibe-coding-workflow/SKILL.md`）与成熟项目手册（AGENTS.md）的实战约束。
> **使用方法**：复制本文件到任意项目根目录（或摘取相关章节进项目的 AGENTS.md/CLAUDE.md）；
> 与项目专属文档冲突时，**以项目专属文档为准**；本文件只提供通用基线，按项目实际裁剪。

---

## 1. 核心理念（一切规则之根）

1. **文档驱动**：项目知识进文件，不只在对话里——需求、设计、任务、进度都要有可查证的文档。
2. **测试先行（红→绿）**：任何改动前先写能**甄别新旧结构**的测试；先确认现有代码跑不过（红），
   只有设想的实现能通过（绿），才动手改实现。测试是契约的权威。
3. **AI 输出视为草稿**：一切自动生成/修改的代码，在 diff、测试、lint、类型检查、运行验证
   全部通过之前，不得视为完成。
4. **小步推进**：任务小到一次实现 pass 能完成、diff 可被独立审阅；越界即失控。
5. **不确定就问**：需求、产品决策、数据契约、破坏性动作、外部依赖不清晰时，停下问用户，
   不擅自决定。

## 2. 标准工作流（每次作业的步骤链）

1. **稳定项目（含 git 前置）**：动工前摸清语言/框架/包管理器/测试命令/lint/构建/现有约定；
   新项目选保守默认，优先团队已熟知的工具链。**git 前置（项目开始前必问）**：
   向用户确认项目 git 远程地址——未提供则先询问（或创建仓库后让用户提供）；
   托管平台为 **GitHub 时必须先启用代理**（git 代理/系统代理/镜像）再执行任何网络操作
   （拉取/推送/Release），代理未确认可用前不做网络动作；Gitee/GitLab 等国内可达平台无需代理。
   若项目尚无专属 AGENTS.md，先按 §8 编写（首个作业的第一件事）。
2. **需求澄清 → 文档链**：`doc/proposal.md`（目标/非目标/用户场景/输入输出/依赖/约束/验收标准/待定问题）。
3. **设计先行**：`doc/high-level-design.md`（架构/模块/数据流/存储/依赖/权衡）+ `doc/detailed-design.md`
   （模块职责/接口契约/文件布局/算法/错误处理/测试规格/边界）；**风险、歧义、备选方案必须写明**，
   不得用自信的措辞掩盖不确定性。
4. **任务拆分**：`doc/tasks/<模块>.md`（目标/涉及文件/步骤/测试/完成定义/依赖）+ `doc/tasks/progress.md`
   （**唯一进度源**，主 agent 维护）。
5. **小步实现**：一次一个未阻塞任务；实现 → 补测试 → 跑该任务检查 → 审阅 git diff → 更新 progress。
6. **验证闭环（含提交）**：全量测试 → lint/类型检查 → 冒烟/运行验证（用户可见行为）→ diff 终检
   （无关改动/生成杂项/密钥泄漏/意外重写）→ **提交前清除垃圾文件并复查工作区（§3.7）** →
   **每次任务完成必 git commit + push 到项目远程地址** → 更新项目状态 →
   汇报（改了啥/验证了啥/剩余风险）。
7. **文档自动同步**：作业完成后自动更新项目专属 AGENTS.md 与 progress.md 的相应章节
   （结构/接口/命令/测试约定/版本发布），无需用户提醒。

## 3. 通用红线（所有场景一律适用）

1. **测试权威，不得迁就实现**：禁止修改测试来让现有实现过关；认为契约有问题时，先改设计文档与
   测试，再改实现。
2. **红→绿纪律**：改动前必写甄别性测试；旧代码也能通过的弱测试视为无效，必须重写到能甄别新旧。
3. **分层纪律**：纯逻辑/核心层保持零副作用、零环境依赖、可单测；UI/IO/副作用薄薄地放在外层胶水。
4. **越界安全返回**：越界/异常输入一律安全返回（undefined/空结果/降级），不抛异常（明确豁免除外）。
5. **最小改动**：只做任务范围内的改动；不顺手重构、不碰其他模块、不覆盖用户已有工作。
6. **敏感信息零入库**：密钥/令牌/凭据/用户数据严禁提交（写入 .gitignore 的本地文件或环境变量；
   脚本只读不打印）。提交前检查工作区。
7. **提交纪律（含提交前清理，显式规则）**：git commit 前**必须先清除文件夹内多余的垃圾文件**
   ——临时/缓存/探测脚本/日志/截图/构建残留/测试与安装残留等，清除后复查工作区；
   git 提交**仅提交构建项目所必需的文档**（源码/文档/测试/构建配置）；
   **禁止提交**：开发过程中残余文件、用户使用与测试信息（用户数据/运行日志/安装清单/安装副本）、
   以及与软件使用和配置无关的一切内容（个人配置、产物、截图）。
8. **清理纪律**：每次作业后清理旧产物、缓存、临时脚本、测试残留目录。
9. **全量回归**：作业完成必跑全量测试（+ 冒烟/构建，见 §5 验证矩阵）。
10. **语言一致**：界面文案、错误信息、日志、提交信息使用团队语言（如中文），保持全项目一致。
11. **详尽日志（修复定位用，显式规则）**：**每次软件运行必须生成便于 bug 修复的详尽日志**——
    记录启动/退出、关键操作路径、错误分类与堆栈、耗时、环境信息（版本/平台/配置）；
    **所有日志统一保存在根目录 `log/` 文件夹**（按日期/会话轮转，不无限膨胀）；
    `log/` 加入 .gitignore（运行时产物，绝不入库）；用户数据与敏感信息脱敏后记录。
    目的：后续每次代码修复时先查 `log/` 即可便捷定位问题位置，无需复现猜测。

## 4. 场景化规则

### 4.1 新项目开发
- 先立**文档链骨架 + 测试基建**，再写功能实现；首个里程碑是「最小可测闭环」（骨架跑通测试 + 提交基线），
  不是功能堆叠。
- 目录分层从第一天就清晰：纯逻辑层 / 表现层 / 装配层（或项目对应的分层）。
- 技术选型保守：无既定工具时选团队熟知的；有既定工具一律沿用。
- 尽早建立 lint、类型检查、CI（如适用），让机器在早期接住低级错误。

### 4.2 Bug 修复（重点：杜绝「修了但没交付」）
1. **先定位根因再动手**：**优先查看根目录 `log/` 下的运行日志**定位问题发生位置与上下文
   （见 §3.11）；可派只读 subagent 排查，但主 agent 必须**亲自复核关键证据**
   （读代码原文与测试，不盲信汇报；复现一次失败路径）。
2. **先写能复现 bug 的甄别性测试**（现有实现必须红）→ 再做**最小修复**（绿）。
3. **补测试盲区**：复盘旧测试为何没拦住（弱断言/空 mock/绕过真实路径），重写为甄别性测试。
4. **回归**：全量测试 + 冒烟 +（若产物是交付物）**必须重新构建产物**——用户安装/部署的是产物，
   源码修复不等于交付修复；并独立校验产物内确实包含修复。
5. 修复不夹带重构；同类型隐患（如同模式监听器）顺带检查，但确认后单独评估。

### 4.3 功能新增
- 文档链先行：proposal → 设计（含接口契约与边界）→ 任务拆分。
- **测试先行定义接口**：先写断言新结构的测试（红），再实现（绿）；接口变更必须同步设计文档
  与测试（先测试后实现）。
- 每任务 ≤1 个模块，subagent 实现、主 agent 审阅 diff；subagent 只碰自己任务文件规定的文件。
- 收尾：更新接口速查/项目结构/命令文档；跑全量回归。

### 4.4 功能删除
- **先查依赖方**：全局搜索引用，确认没有其他模块/文档依赖被删结构。
- **契约同步**：删除对应测试断言；设计文档标注「删除契约」并保留于历史；测试不得再断言已删结构。
- 删除死代码、残留引用、相关样式与文档条目；回归全量测试。

### 4.5 重构
- **行为不变原则**：重构不得改变可观测行为；先有覆盖测试作行为契约。
- 逐模块小步推进，每步独立提交；每步后跑全量回归 + lint/类型检查。
- 重构与修 bug 分开进行，绝不混在一次改动里。

### 4.6 版本发布
- 按 semver 提升版本（package.json/构建配置同步）→ 全量验证 → 构建产物（唯一、带版本号）。
- `git tag v<version>` 推送 → 发布平台（GitHub/Gitee 等）创建 Release 并上传产物；
  **脚本化 + 幂等**（tag 已发布则拒绝覆盖，以平台 Release 列表为准判定，不可凭 git tag 存在判定）。
- 发布后**独立验证**：公开 API/下载 URL 检查产物可达、大小正确。
- 发布凭据管理：令牌存 .gitignore 本地文件或环境变量，严禁入库/打印；令牌轮换后同步替换
  并在进度文档记录。
- 重大版本更新后自动同步项目文档中的版本与发布信息。

### 4.7 子 Agent 分配规则
- **适合派子 agent**：边界清晰、可独立审阅的任务——单模块实现、定向 bug 排查（只读）、
  测试编写、文档/任务文件撰写。
- **必须留在主 agent**：跨模块协调、集成审阅、**根因复核**（子 agent 的排查结论必须由主 agent
  亲自读代码复核证据后再采信）、提交推送、进度与文档同步、需求决策。
- **权限边界**：子 agent 只做自己任务文件规定的文件，不碰其他任务的文件；不 git commit/push；
  不留调试残留（console.log 等）；**汇报真实结果**（含失败与阻塞），不得虚报。
- **并行与依赖**：无依赖的任务并行派发；有依赖必须等待前序完成；同一批文件绝不并行修改。
- **规模纪律**：单点小修复/一两行/单文件改动不派子 agent——协调与转述成本高于直接严谨执行，
  多 agent 传递反而易引入二次偏差（bug 叠加）。

## 5. 验证矩阵（「作业完成」的定义）

| 改动类型 | 必做验证 | 说明 |
|---|---|---|
| 任何改动 | 全量测试 + diff 终检 + 文档同步 | 测试必须全绿；diff 无杂项/密钥/意外重写 |
| 用户可见行为 | + 冒烟/实际运行验证 | 页面加载、无 JS/运行时错误、关键路径走通 |
| 交付物相关 | + 重新构建产物 | 安装包/构建物必须包含本次改动 |
| 重大版本 | + Release 发布与独立验证 | tag + 上传 + 下载 URL 验证 |
| 纯文档 | 免构建/重打包 | 但提交推送必须 |

## 6. 提交信息规范

- 格式：`<type>: <中文/团队语言描述>`；type ∈ feat / fix / docs / refactor / test / chore / perf。
- 一条提交一个逻辑变更；描述写**为什么**（根因、影响面），关键决策可展开说明。
- 提交前 `git status --short` 复查：无多余文件、无敏感信息、无构建产物。

---

## 7. 常见反面教训（复盘沉淀）

- 修复未重新构建产物 → 用户复装旧包，症状依旧（「作业完成闭环」的由来）。
- 测试用空 mock 只断言「函数被调用」、不查真实效果 → bug 全绿放行（弱测试红线）。
- 页面交互在「打开/关闭」同一次事件分发内完成 → 用户视角毫无变化（真实事件流测试的必要性）。
- 幂等判断用错依据（git tag 存在 ≠ Release 已发布）→ 发布重复或误拦（以平台数据为准）。
- URL 拼接想当然（双问号/缺参数）→ API 400（自测真实请求，不只靠读代码）。
- 强杀进程（process.exit）撞运行时句柄清理 → 崩溃掩盖真实错误（让事件循环自然排空）。

## 8. 项目专属 AGENTS.md 编写指导（所有任务开始前的第一件事）

**目标**：基于用户提供的信息，在**任何任务开始之前**写出一份专属本项目的 AGENTS.md，
让之后的新会话**只读它即可接管全部开发**——命令、结构、纪律、发布全部自包含。

**信息收集（写前必问）**：
- 项目定位与一句话简介；目标用户/运行形态（桌面/网页/服务/库？）
- 技术栈、框架、包管理器；启动/测试/构建/lint 命令
- 目录结构现状（或期望分层：纯逻辑层/表现层/装配层）
- **git 远程地址与托管平台**（GitHub 需代理，见 §2.1）；交付形态（安装包/镜像/制品）
- 团队语言（界面/注释/提交信息用什么语言）；已知红线与偏好
- 项目成熟度与既有文档（有则先读，无则从零建）

**章节大纲（按此写，逐节要点）**：
1. **项目概览**：一句话定位 + 核心特性清单 + 技术栈 + 交付形态
2. **工作流程**：文档链 → 测试先行（红→绿）→ 任务拆分 → 验证闭环 → 集成验证 →
   版本发布 → 文档自动同步（从本文件 §2 摘取，替换成本项目具体命令与产物）
3. **规则（护栏）**：本文件 §3 全部红线 + 项目特有补充（如发布令牌管理、代理要求）
4. **项目结构**：目录树 + 每个目录/关键文件一行职责（与实际代码逐项核对）
5. **模块接口速查**：关键模块导出签名——写完用 `grep -n "^export"` 与实际签名核对，
   杜绝文档与代码漂移
6. **常用命令**：启动/测试/冒烟/构建/打包/发布/代理配置，逐条给出实际命令与产物说明
7. **测试约定**：测试框架/运行环境（jsdom/node 等）/文件与模块对应关系/注入与 mock 模式
8. **已知弱点与改进建议**：诚实评估（基于实测数据，不写空话），标注「实施前须走文档链」

**编写要求**：全部中文（按团队语言）；数字与命令写实际值（用例数、产物名、大小）；
与代码不一致宁缺毋滥；**每次作业后自动同步**（§2 第 7 步），保证它始终可用。

**验收标准**：新会话仅加载该 AGENTS.md（不翻代码）→ 能正确跑通常用命令、定位到任意模块、
按纪律完成一个作业闭环（改代码→测试→构建→提交→必要时发布），全程无需用户补充说明。
